## Does a wired client crossing the mesh use offload?

**It can.** In the tested custom firmware, Linux bridge and connection-tracking hooks identify eligible established TCP or bidirectional UDP flows between registered bridge ports. The NSS bridge code can install a five-tuple bridge flow that preserves Ethernet addresses and IP TTL rather than routing or NAT. The mesh interface maps to an NSS encapsulation node; the firmware mesh also has separate virtual-device and decapsulation nodes. Linux remains the control plane, while eligible packets may use the NSS network processor’s firmware fast path. Initial packets, ARP, broadcast and unadmitted or unsupported flows may follow host or other paths.

A read-only live inspection showed the relevant wired and mesh ports armed, a bridged TCP flow installed between the wired and mesh encapsulation interfaces, and firmware activity in both directions. This demonstrates admission and some firmware activity, not that every client flow or all throughput was offloaded. A separate installed UDP flow was observed but was not identified as the client flow. Wi-Fi NSS was enabled; the Ethernet-only NSS backend being disabled does not rule out mixed Ethernet/Wi-Fi offload. No new traffic, configuration change or reboot was used for this inspection.
